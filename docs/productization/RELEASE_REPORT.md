1. **Before productization.** M0–M6 investigated bundled synthetic payment integrations with fixed event vocabulary, SQLite business tables, six invariants, versioned schedules, isolation, DNA, replay, verification and reduction. Those contracts, historical evidence and Git history remain intact.

2. **External capability.** Owned applications outside the repository can now declare a strict local TOML manifest, application argv/cwd, fixtures, JSON webhook delivery, readiness, observer and business contract. Managed targets use fresh processes, ports, signing secrets and state. Explicit staging allowlisting/authorization is separate and remains INCONCLUSIVE without writer-quiescence evidence.

3. **Adapter architecture.** `external.manifest` validates configuration; `external.lifecycle` extends the existing supervisor's preparation/start/delivery/observation hooks and inherits confirmed group settlement; the existing dispatcher accepts an HTTP request builder. `external.observers` provides scoped read-only SQLite/PostgreSQL snapshots. `external.services` is shared by CLI and local web routes. Existing payment services/oracle/artifacts retain their original path.

4. **Invariant contract.** Strict version 1 definitions support uniqueness, references, expected effects, permitted/required transitions, related values/capacity, ownership scope, and acknowledgement consistency. Evidence distinguishes satisfied/violated/not-evaluable/invalid. Missing state cannot become PASS. Acknowledgements are bound to actual delivery responses, and duplicates do not imply a new write for each 2xx. No eval or caller SQL is used.

5. **Independent application.** A separate local Git repository, `Duress-ticketing`, owns its package, schema, Docker/Compose setup, tests and business logic. Its history through `d7c646c` is delivered in `examples/ticketing.bundle`; no additional public repository was created. Normal/fixed variants use PostgreSQL transactions, locks and uniqueness; the deliberately flawed variant exposes a real check/write race. This is accurately labelled AI-assisted development, not an unrelated human author’s experiment.

6. **External investigation.** Actual PostgreSQL state showed three tickets for one booking and a two-seat event under concurrent duplicates. The flawed control failed five valid trials. The corrected full nine-scenario suite covers normal, sequential/concurrent/cross-event duplicates, ambiguous acknowledgement retries, delays, out-of-order events, invalid data and invalid signatures. Expected HTTP errors are distinguished from business failures.

7. **DNA and portability.** `external-dna@1` preserves exact event bytes, fixtures, declarative definitions, schedules, expectations, failure signatures, measured samples and type-aware observed schema provenance. Code identity covers the entire package Python implementation and versioned semantics, including inherited settlement and aggregation. Credentials, commands, directories and destination origins are resolved locally. Changed artifacts/rules/code are refused before business delivery. A clean installed wheel reproduced the actual failure in ten fresh trials.

8. **Fix verification and reduction.** The installed-wheel control reproduced five failures; the corrected candidate passed twenty valid trials and was VERIFIED. A flawed-as-candidate negative control was NOT_VERIFIED. Reduction removed one of three concurrent deliveries, preserved the two-way race and independently revalidated it; the exported reduced artifact receives a separate artifact-only replay. These are bounded empirical claims, not proof of universal reliability or global minimality.

9. **Installation/onboarding.** Wheel and sdist build for Python 3.12. Packaged targets, cache fixtures, showcase, templates and static assets work outside a checkout. A fresh environment ran `init`, read-only `doctor`, and an actual five-trial starter `check`. The external application was independently cloned and installed outside Duress. Required command documentation is in EXTERNAL_PROJECTS.md.

10. **CI.** Reusable GitHub Actions installs Duress and the owned application, starts password-protected loopback PostgreSQL, validates paths, executes real checks and preserves JSON/JUnit/DNA on failure. Expected exit codes are 0 PASS, 1 FAIL, 2 INCONCLUSIVE, 3 configuration/operational error and 4 REJECTED. The reusable corrected-reference job was observed passing; the comprehensive PR job additionally runs real flawed/fixed/replay/verification controls. The PR check view contains the final remote result and artifact links. No branch-protection settings were changed without a repository-owner decision.

11. **Regression/compatibility.** The development broad gate passed 723 tests, with slow/browser excluded, while implementation was ongoing. The final targeted external gate passed 88 tests; the final Linux focused gate passed 106. All ten existing browser tests and three historical slow experiments passed. The final PR workflow exercises the complete current suite. Historical measurement/release files have no changes against the starting main.

12. **Operations and privacy.** Project-scoped records use schema/integrity checks, atomic writes, safe identifiers, symlink refusal, corruption diagnostics, owner-aware queued/running recovery, retention dry-runs and explicit export/import. The workbench reconciles proven orphans at startup and preserves live owners. Init and serve groups have bounded cleanup, process-table confirmation, count/RSS monitoring and OS resource limits. PID-file failure and proxy negative controls have tests. Credential-like fixtures/observation columns are refused; returned and persisted data are redacted. A real SELECT-only login could read but not insert. No trial schemas remained after the clean controls.

13. **Deployment.** Docker builds and serves health, HTML, targets and assets. Hosted external execution is refused with 403. Linux tests run in the image. Render configuration is retained, but no authenticated Render credential/session was available, so public deployment remains explicitly unverified. No package-index upload was performed.

14. **Git delivery.** Meaningful checkpoints on `feat/productization-byoi` were pushed normally; no history was rewritten. PR #2 is registered with this T3 thread. The separate application remains a local repository plus a reproducible Git bundle. Merge is conditional on the defined acceptance gates and final required checks; the PR records the final branch/merge status.

15. **Documentation/demonstration.** README, external manifest/contract, storage, web and CI guides are current. `EVIDENCE.md` records commands, versions, positive/negative results and development corrections. `clean-install/` retains actual installed-wheel records; `core-freeze.json` checks that integration required no engine edits. Authentic browser screenshots and self-contained report export are included. Historical demonstrations remain labelled historical.

16. **Limitations and external prerequisites.** Staging lacks verified quiescence and intentionally remains INCONCLUSIVE. External delivery currently requires direct network access and default trusted TLS certificates; custom proxy/CA environments are unsupported. External AI proposal selection is not implemented; deterministic manifest scenarios are the supported external workflow. Local supervision is not a hostile-code sandbox; macOS memory monitoring is periodic RSS enforcement. Hosted metadata is single-worker/ephemeral, with no multi-tenant external execution. Render authentication and package-index publication remain external release steps, not claimed successes. The only readiness decision is the one backed by completed PR acceptance evidence.

17. **Launch acceptance.** The decisive local capability is implemented and empirically exercised: an application outside Duress, independently configured business contracts, real persisted failure, portable reproduction and empirical correction verification without domain-specific engine changes. `core-freeze.json`, installed-wheel artifacts and the PR's actual CI controls support this claim. The final READY / NOT YET READY disposition is supplied in the PR completion report and user handoff after all required gates finish.
